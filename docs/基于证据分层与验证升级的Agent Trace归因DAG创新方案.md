# 基于证据分层与验证升级的 Agent Trace 归因 DAG 创新方案

## 摘要

本方案面向**企业客服与运营工单的多 Agent 闭环**：一个用户问题或内部请求经调度 Agent 分派，由知识检索、规则/合规校验、工单操作和质检 Agent 协同处理，最终给出答复、创建/更新工单或完成受控业务操作。该场景中的错误会直接表现为答复错误、SOP/合规不通过、工具调用失败、业务字段写错或工单未闭环；企业需要在短时间内确认“谁在何时做错了什么、证据是什么、修复后是否有效”。

本方案提出 Evidence-Governed Attribution DAG（**EGA-DAG，证据治理归因 DAG**）：将这类生产 Agent 失败归因从“让模型阅读一段日志后直接给出根因”的一次性判断，转化为一套**可持久化、可查询、可审计、可按需验证**的归因证据系统。

它把同一条失败结论所依赖的信息严格分为四层：原始 Trace、观测/插桩声明的结构关系、规则或模型推断的依赖假设、归因审计与反事实重放结果。系统始终保留全量事件作为最终根因候选；图边只用于组织证据、安排审计和分配重放预算，不能在早期阶段排除某个候选。只有在可复现重放中修复候选步骤、并由任务成功 oracle 观察到成功结果时，结论才从“合理怀疑”升级为“经干预支持的因果证据”。

该方案的核心不在于再提出一种仅靠 LLM 构图的根因定位算法，而在于建立一条证据升级链：

```text
原始执行事实 → 依赖假设 → handoff 责任审计 → 受控重放 / oracle 验证
       可观察             可解释                 可检验
```

它可承载 DeFA 式失败传播、BLADE 式 handoff 审计和 CAR 式干预重放：前两者负责低成本发现和解释候选，后者为少量高价值结论提供强因果验证。本文是本项目的候选系统创新方案；其定位、效果与成本仍须通过实现和基准实验验证。

## 商业落地场景与客户价值

### 首个产品化场景：企业客服与运营工单的多 Agent 闭环

首期不把 EGA-DAG 定位为面向所有 Agent 的泛化“根因算法”，而是聚焦于**有明确任务边界、可留存 Trace、可定义业务验收结果**的企业工单场景。典型工作流如下：

```text
用户 / 员工请求
        │
        ▼
调度 Agent ──► 知识检索 Agent ──► 规则 / 合规 Agent
        │                                      │
        └────────► 工单 / CRM 操作 Agent ◄──────┘
                              │
                              ▼
                        质检 Agent / 业务验收
```

一个工单完成后，系统已有可观测的业务结果，例如：工单字段是否符合规则、调用是否被后端接受、回复是否覆盖必填信息、是否在 SLA 内闭环、是否被人工质检打回。这些结果可以构成 `TaskOracle`，或至少形成可审核的业务失败信号。相比开放式聊天，这类场景既有真实商业价值，也更适合作为反事实重放与高可信归因的首个试点。

| 角色 | 在场景中的职责 | 从 EGA-DAG 获得的交付物 |
|---|---|---|
| 采购方：企业 AI 平台 / 智能客服负责人 | 对 Agent 成本、质量、合规和稳定性负责 | 可量化的失败分布、责任归属、治理报表和上线风险依据 |
| 使用者：Agent 开发与运维人员 | 处理线上失败、修改 prompt / tool / workflow | 带证据路径的 Who / When / What、建议先修复的位置、可复现回执 |
| 使用者：业务质检与流程负责人 | 审核错误答复、越权操作和工单闭环质量 | 可回放的业务上下文、责任 handoff、可审计的处置记录 |
| 终端客户或业务人员 | 提交服务请求并接收处理结果 | 更少的错误答复、漏办工单与人工转派，不直接面对归因系统 |

商业闭环不是“发现一次日志异常”即结束，而是：**线上失败告警 → 证据化归因 → 开发/运营修复 → 沙箱或回放验证 → 将已验证案例沉淀为回归集与质量规则**。这使平台可以从观测产品延伸为 Agent 质量治理产品。

### 两级服务边界

| 服务级别 | 面向的业务情况 | 系统承诺的结果 | 不作出的承诺 |
|---|---|---|---|
| 在线归因与审计 | 所有生产失败 Trace，包括没有严格成功 oracle 的真实工单 | 快速给出候选 Who / When / What、证据等级和人工复核入口 | 不把 LLM 判断包装为已证明的因果根因 |
| 验证型归因 | 能在脱敏沙箱或录制工具环境中重放、且有明确验收规则的高价值问题 | 给出修复候选后的重放结果、oracle 结论和可验证回执 | 不在生产环境自动重复执行有副作用的外部操作 |

这一区分使产品能先服务全部线上问题，再将“经干预支持”的高可信结论用在高风险工单、版本发布审核和回归测试中。

### 产品形态与商业价值

EGA-DAG 可以作为现有 OTel / Agent Insight 等观测系统之上的归因服务：观测系统负责采集 Trace，EGA-DAG 负责版本化图、归因、验证和治理回执。首期产品可拆为三层能力：

| 产品能力 | 交付内容 | 直接商业价值 |
|---|---|---|
| Trace 归因工作台 | 失败列表、Who/When/What、证据路径、责任 Agent/工具视图 | 缩短开发与运维人员从失败 Trace 定位可修改位置的时间 |
| 质量治理与回归包 | 按租户、流程、Agent、工具、错误模式聚合；沉淀已验证失败用例 | 把人工复盘转化为可复用的发布门禁和质量资产 |
| 受控验证服务 | 沙箱重放、补丁试验、oracle 和 `AttributionReceipt` | 为高风险流程提供“修复有效”的证据，降低盲目改 prompt 或 workflow 的风险 |

首期价值应以人工排障时长、人工质检工作量、失败重复率、发布后回归率和高风险问题的验证覆盖率衡量；这些是待试点验证的业务指标，而不是预先承诺的固定收益。

## 现状

企业多 Agent 工单平台通常以 span 树、时间序事件或文本日志保存执行过程。它能够回答“执行过什么”，却难以稳定回答“哪一步是决定性错误、应由哪个 Agent / 工具负责人处理、证据是什么、这个结论是否真的经得起修复后重跑的检验”。直接按时间倒序阅读日志存在三个根本问题：

- 最终报错步骤往往只是上游错误传播后的症状，时间上靠后不等于因果上更接近根因。
- Agent 的委托、工具结果、消息引用、共享工件和重试交织在一起；仅有 parent-child span 关系不足以恢复信息依赖。
- LLM 可以从语义上猜测依赖或责任，但其输出本身是推断，不应与“该事件真实发生”“该输入确实被传递”混为一谈。

当前已有方法分别覆盖归因链的不同环节：DeFA 通过依赖和失败传播图缩小候选；BLADE 审计上游信息是否被下游决策错误使用；CAR 通过 do 干预和重放测量改变候选步骤后的任务结果。它们共同指出，结构化 Trace 有利于归因；但单次模型判断不能自动成为因果证明，而全量重放又昂贵且需要稳定的运行环境。

本项目已形成 Agent Trace 的树形查询、六类派生图视图和边证据等级的数据/查询设计：执行、依赖、委托、因果假设、数据流与偏序图，节点可回链到 `source_span_id`。这套能力目前是数据模型与查询设计，尚不是一个完成的归因算法。它的缺口是：**如何让图上的每一条归因证据有明确来源、版本、强度和可验证路径。**

## 为什么要做证据治理归因 DAG

第一层原因是归因正确性。执行顺序、数据依赖、责任归属和因果效应是四种不同关系。系统若把 LLM 推断出的 `CAUSES` 边直接当作执行事实，会把相关性误报为因果性；反之，若只保留原始日志，又无法跨 Agent、工具和工件解释错误如何传播。

第二层原因是可复现性。一次归因结论需要能回答：它基于哪一版 Trace、用了哪些边、哪些边来自插桩或模型、模型和 prompt 是什么、是否做过真实重放、oracle 返回了什么。没有这些信息，同一条结论无法复核，也无法公平比较不同归因方法。

第三层原因是成本控制。全量 LLM Judge 会消耗长上下文与推理预算；对每一个 step 做反事实重放的代价更高。应当用图先组织候选和局部审计，再只对 Top-K 高价值候选执行重放验证。

第四层原因是方法可插拔。项目不能把存储层绑定为某一篇论文的 prompt 或某一个模型。DeFA、BLADE、规则引擎和后续的学习式归因器应共享同一份 Trace 事实与图版本；不同方法的输出以派生数据并存，从而可比较、可回查、可替换。

第五层原因是业务治理。生产工单通常涉及客户信息、流程权限和人工审核。企业不仅需要“模型认为谁有错”，还需要一份可交给研发、运维、质检和审计人员的回执：错误影响了哪一类业务、由谁处理、是否触及敏感数据、修复是否已在受控环境验证。

## EGA-DAG 方案

### 1. 总体定位

EGA-DAG 定位为企业 AgentOps 平台中的“**证据治理归因与验证控制面**”，位于 Trace 摄入、图查询、归因算法、工单处置与可控重放环境之间：

```text
OTel / Agent Runtime / Tool Runtime
                │
                ▼
      L0 原始不可变 Trace（事实来源）
                │
                ▼
L1 观测/声明结构图 ──► L2 依赖假设图 ──► L3 审计、结论与重放证据
       │                       │                         │
       └────── 图查询、候选生成、审计预算 ────────────────┘
                                                     │
                                                     ▼
AttributionReceipt：可审计归因回执 ──► 工单处置 / 回归测试 / 发布治理
```

它不替代 Agent runtime、任务执行器或任务成功 oracle；也不预设某一种根因算法。Trace 系统负责记录执行事实和保存版本化图数据，归因算子负责发现与排序候选，重放执行器负责对少数候选做受控干预，oracle 负责判断任务是否成功。业务工单系统只接收归因回执和处置建议，是否修改 prompt、禁用工具、回滚流程或通知人工，仍由既有权限和审批流程决定。

### 2. 核心对象

| 对象 | 含义 | 关键字段与约束 |
|---|---|---|
| `TraceFact` | 原始不可变事件或 span | `trace_id`、`source_span_id`、时间、actor、payload 摘要/哈希、原始位置；只追加，不被推断结果修改 |
| `BusinessCase` | 与业务工单对应的执行上下文 | `tenant_id`、`case_id`、流程版本、数据分级、业务 owner、SLA、处置状态；原始客户数据按权限回链，不复制到推断结果 |
| `StructuralEdge` | 观测到或插桩声明的执行关系 | `CALLS`、`NEXT`、`DELEGATES_TO`、`PRODUCES`、`CONSUMES`；记录 `observed` 或 `declared` 来源及证据指针 |
| `DependencyEdge` | 规则或模型推断出的依赖假设 | `DEPENDS_ON`、`REPEATS`、`CONTRADICTS`、`REPAIRS` 等；必须含置信度、提取器、模型/规则版本、输入图版本和证据 span |
| `Requirement` | 任务目标、约束或验收条件 | 任务文本、版本、来源；有明确成功判据时关联 `TaskOracle` |
| `HandoffAudit` | 上游信息到下游决策的责任审计 | `source_span`、`decision_span`、`breach / inherited / repaired / kept`、理由、概率、关联 requirement |
| `AttributionRun` | 一次归因算法运行 | 方法、输入图修订号、候选全集、排序、Who/When/What、模型与 prompt 版本 |
| `CounterfactualRun` | 一次受控干预及其重放 | 候选步骤、补丁、重放配方、环境/状态哈希、fidelity 状态、oracle 结果、重复运行统计 |
| `AttributionReceipt` | 面向人和系统的最终回执 | 归因结论、证据路径、结论等级、复现信息、跳过/失败原因和成本 |

`TraceFact` 与 `StructuralEdge` 是系统的事实底座；`DependencyEdge`、`HandoffAudit` 和 `AttributionRun` 都是版本化派生数据。任何算法只能新增或废弃派生记录，不能覆盖原始事实。

### 3. 四层证据 DAG

| 层 | 保存内容 | 证据性质 | 对归因的作用 |
|---|---|---|---|
| L0：原始 Trace 层 | span/event、消息、工具请求与结果、artifact、时间、父子关系 | 不可变执行记录 | 可回到原始上下文，防止摘要或模型输出成为唯一依据 |
| L1：结构事实层 | 调用、顺序、显式委托、显式输入输出、工件产生/消费 | `observed` 或 `declared` | 提供确定性遍历与可解释的事实骨架 |
| L2：依赖假设层 | 语义依赖、冲突、重复、修复、失败传播候选 | `inferred` | 为候选排序、局部审计和长轨迹切片提供线索 |
| L3：审计与验证层 | handoff 审计、归因排序、补丁、重放、oracle 结果 | `audited` 或 `intervention-supported` | 输出可说明证据强度的归因结论 |

边和结论除了层次，还应保留统一的 `evidence_grade`：

```text
observed / declared
        ↓
inferred                 （模型或规则提出的依赖假设）
        ↓
audited                  （审计到信息被怎样使用）
        ↓
intervention-supported   （受控重放中由 oracle 支持）
```

这不是把后一等级当作前一等级的“覆盖”。例如，一个 `intervention-supported` 结论仍须回链至其 L0 原始事件、L1 数据流和 L2/L3 推理过程；系统展示时应同时显示证据来源与不确定性。

### 4. 归因协议：候选保留、审计限额、验证升级

一次失败归因按以下协议执行：

```text
1. 固化 TraceRevision：规范化 span、事件、Agent、Artifact，并建立 L1 事实边
2. 保留全量候选：该 Trace 中每个可归因 event / span 都能成为最终 When
3. 生成 L2：确定性规则优先，LLM 仅补充跨语义依赖，并写入置信度与版本
4. 分配审计预算：为关键决策选择少量高价值上游 handoff，写入 HandoffAudit
5. 全局裁决：在全量候选上排序，输出 Who / When / What 及完整证据路径
6. 验证升级：对 Top-K 候选执行受控修复重放，以 oracle 结果更新结论等级
7. 产出回执：固化本次输入、模型、边版本、审计、重放与成本
```

步骤 3 和步骤 4 可以显著减少长轨迹中的模型阅读量，但不能把未进入依赖图或未被审计的步骤从最终候选空间删除。这一“候选保留”原则吸收了 BLADE 的优点：局部图构建主要决定**先看哪里**，而不是预先决定**根因只能在哪里**。

### 5. handoff 审计：将“存在依赖”与“错误使用信息”分开

依赖边仅表示下游决策可能参考了某个上游事件，不能判断责任归属。EGA-DAG 将责任判断表达为独立的 `HandoffAudit`，审计对象为 `source → decision`：

| 审计标签 | 含义 | 对排序的影响 |
|---|---|---|
| `kept` | 下游正确使用了上游信息 | 降低该 handoff 的责任怀疑度 |
| `breach` | 下游误读、遗漏、篡改或违背了上游信息/任务要求 | 提高下游决策作为根因候选的优先级 |
| `inherited` | 下游忠实继承了已经错误的上游信息 | 更应回溯上游来源，不能把下游当作唯一根因 |
| `repaired` | 下游识别并修正了上游问题 | 切断或削弱该路径上的失败传播 |

例如，步骤 12 的工具返回正确数值，步骤 16 的 Agent 将其单位误读，步骤 19 输出错误答案：

```text
12 工具结果 ──PRODUCES / DEPENDS_ON──▶ 16 决策 ──影响──▶ 19 最终答案
                                     │
                          HandoffAudit = breach（单位误读）
```

这时 L1/L2 说明 12 的数据确实到达了 16，审计说明错误发生在 16 对信息的使用方式，而不是把“上游参与了决策”误判为“上游生成了错误”。

### 6. 反事实验证栅栏：把合理解释升级为因果证据

对 Top-K 候选，系统可接入 CAR 式重放，但必须先通过 `ReplayFidelityGate`：

```text
1. 从 TraceRevision 取回候选步骤之前的成功前缀及其必要状态
2. 校验输入、Agent/工具版本、模型配置、关键 artifact 与环境状态 hash
3. 在受控环境中精确回放前缀；不能达到预期状态则标记 fidelity 失败，不做因果声明
4. 仅替换候选步骤的输出、动作或决策补丁，保留其余条件
5. 从该点续跑后缀，由 TaskOracle 判断任务成功/失败
6. 必要时多次运行，报告成功率、方差和置信区间，而非只报一次结果
```

步骤 5 得到“修复步骤 16 后任务成功”时，能支持“步骤 16 的修复在该重放条件下对成功充分”。对于随机 Agent、多重错误或环境漂移，它不自动证明步骤 16 是唯一根因；因此回执应记录为 **intervention-supported**，并带上重放次数和适用前提。若没有明确 oracle 或不能稳定重放，系统仍可输出 `inferred` / `audited` 结论，但不能升级为强因果结论。

在上例中，若修复步骤 16 的单位解释后续跑成功，步骤 16 获得经干预支持的证据；步骤 12 因产生了正确输入，不应被该验证归为决定性错误。

### 7. 归因回执与查询能力

每一次归因必须生成不可变 `AttributionReceipt`，至少包含：

- 使用的 `trace_revision`、原始 `source_span_id` 和候选全集范围；
- 选中的 Who / When / What 及其排名和置信度；
- 支撑结论的事实边、推断边、handoff 审计和完整证据路径；
- 规则、模型、prompt、参数、代码/数据版本；
- 反事实补丁、重放环境、fidelity 状态、oracle 输出与重复试验统计；
- 未能验证、被跳过或发生漂移的原因，以及本次 LLM / 重放成本。

这让系统能支持以下可复用查询负载，而不是只展示一段自然语言解释：

```text
给定最终失败事件，沿 evidence_grade ≥ declared 的边回溯有哪些事实来源？
哪些 handoff 被审计为 breach，且位于失败事件的依赖祖先路径上？
某个 Agent 在多个失败 Trace 中有多少 intervention-supported 的决定性步骤？
两个归因算法在同一 TraceRevision 上选了不同 When，它们分别使用了哪些不同证据？
哪些结论只有 inferred 证据、尚未满足 replay fidelity，因此不能用于高可信标签？
```

查询执行可复用项目已有的物化路径、结构索引与图边邻接索引。归因 DAG 不需要改变树作为摄入事实的地位：树结构同步维护；依赖推断、审计和重放结果均为异步、可版本化的派生视图。

### 8. 默认安全策略

- L0 原始 Trace 只追加；任何模型输出均不得更新、删除或重写事实边。
- 结构边、推断边、审计和归因回执都必须带来源、版本、时间和证据指针；图版本不可被静默覆盖。
- 无法建立可靠依赖时，记录“证据不足”或保持未连接状态；不以低置信度边伪造完整因果链。
- 图构建与局部审计只能影响排序和验证预算，不能剥夺全量事件成为最终候选的资格。
- 重放默认在隔离环境执行；具备副作用的工具调用使用 stub、录制响应或显式审批，避免归因操作触发真实工单写入、外部调用或凭据泄露。
- 原始 prompt、工具参数和 artifact 按数据分级脱敏/加密保存；归因回执优先存引用、摘要和哈希，而非无控制复制客户信息、敏感工单内容或凭据。
- 所有图、回执和重放资产都以 `tenant_id` 和数据分级隔离；业务人员只能访问其授权流程，平台管理员也不默认获得原始客户 payload 的查看权限。

### 9. 分阶段落地

第一阶段以一个具体的企业工单流程试点建立事实与回执闭环：完成 `BusinessCase`、`TraceFact`、L1 `StructuralEdge`、`TraceRevision` 和 `AttributionReceipt` 的存储模型；将现有 Trace 统一映射为 event、Agent、Artifact 与可回链 `source_span_id`，并以 All-at-Once 作为无图基线。目标是保证同一输入可复现、可查询、可比较，并能把失败结论交付给实际处理人。

第二阶段建立低成本归因证据：实现确定性依赖规则、L2 推断边版本化、DeFA 式失败传播切片和 BLADE 式 `HandoffAudit`。目标是评估候选召回、审计成本、解释完整度与 Who/When/What 定位效果，而不把审计结果误报为因果事实。

第三阶段接入验证升级：实现 `ReplayFidelityGate`、重放配方、候选补丁和 `TaskOracle` 适配器；优先选择无副作用、可稳定重放、具有任务成功判据的受控任务。目标是报告 Top-K 候选的可重放率、fidelity 通过率和经干预支持比例。

第四阶段形成业务与数据闭环：在 Who&When Pro 等受控注错数据和试点流程的真实自然失败 Trace 上分别报告结果；将经稳定重放支持的结论沉淀为高可信标签、回归测试和发布门禁，但必须与人工自然失败标签分开统计。试点达成稳定审计与验证流程后，再扩展到其他业务 Agent，而非一开始覆盖所有类型的工作流。

### 10. 可观测指标

| 类别 | 建议指标 |
|---|---|
| 归因效果 | Who、When、What 与联合指标；错误模式采用 Macro-F1；按框架、任务族、模态和轨迹长度分桶 |
| 候选与审计 | 全量候选数、图/审计后的 Top-K 召回、每条 Trace 的依赖边数、审计覆盖率、`breach / inherited / repaired / kept` 分布 |
| 因果验证 | 可重放率、fidelity 通过率、Top-K 验证命中率、修复后成功率变化、重放次数和置信区间 |
| 数据质量 | observed/declared/inferred 边占比、低置信度边比例、缺失 `source_span_id` 比例、图版本漂移率 |
| 系统成本 | 摄入与构图延迟、结构/图查询 p95、LLM token 与时延、每个 intervention-supported 结论的重放成本 |
| 可审计性 | 回执完整率、结论可回链至 L0 的比例、模型/规则/环境版本缺失率 |
| 业务价值 | 人工排障时长、人工质检工作量、重复失败率、发布后回归率、高风险工单的验证覆盖率；按租户和流程分别观察 |

## 风险与边界

EGA-DAG 把“因果”限制为有证据等级的声明，而不是将所有依赖图命名为因果图。L1 的 `observed` 表示事件或插桩记录存在，`declared` 表示 runtime 声明了关系；它们仍不等价于“该关系在语义上决定了失败”。L2/L3 的模型判断应始终以推断或审计方式展示。

重放验证依赖可控状态和任务 oracle。外部网页、时间相关服务、不可录制工具、随机采样和多错误交互都会降低可验证性；fidelity 失败是有价值的运行结果，应被记录为“无法验证”，而不是被隐藏或强行给出结论。

Agent 执行中可能有循环、重试和反复消息。EGA-DAG 以“带版本的事件实例”而不是抽象 Agent 名称作为图节点，所有结构与依赖边指向具体时间上的 event version；重试由多个事件节点表示，因此单次 TraceRevision 仍可形成沿执行时间和信息版本前进的 DAG。跨 Trace 聚合图另行建立，不能与单次执行 DAG 混为一谈。

最后，本方案的创新定位是企业 AgentOps 中的系统级证据管理与验证编排，而不是声称单独发明了依赖推断、LLM 审计或反事实重放。首期商业边界是“企业客服与运营工单的多 Agent 闭环”，不包含面向终端用户的通用聊天产品，也不替代业务系统自身的权限、审批或异常处置机制。真正的差异化要由端到端试点证明：在相同 Trace、相同模型预算和相同验证条件下，EGA-DAG 是否能以更低成本给出更可复现、更高可信、且能缩短真实处置链路的归因结论。
