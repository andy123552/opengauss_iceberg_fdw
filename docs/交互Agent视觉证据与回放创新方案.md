# 交互 Agent 视觉证据与回放创新方案

## 摘要

本方案面向需要“看屏幕—理解状态—调用工具—改变环境”的长时交互 Agent，提出**视觉证据包与决策回执（Visual Evidence Pack & Decision Receipt，VEP-DR）**。它将每一次会改变环境的 Agent 决策，组织成可重建、可审计、可验证的视觉证据单元。

交互 Agent 可以按需保存初始帧、动作后帧、动画帧和裁剪图，并主动选择回看哪一帧、哪个区域或哪些像素。已有运行时 TraceStore 已能提供 `run → step → tool_call → observation → asset` 的基础契约、内容寻址去重与来源关系；本方案进一步回答传统截图留档与普通轨迹记录尚未直接回答的问题：

```text
一次动作真正收到过哪些视觉 / 结构化证据？
这些证据来自当前画面、历史画面还是派生裁剪？
若要复现该动作，应以什么顺序重建哪些输入与环境状态？
去掉或替换某个视觉证据后，模型的决策和任务结果是否变化？
```

VEP-DR 不把模型自然语言解释或思维链当作因果证明。它记录的是**宿主可观测的证据交付事实**：哪些资产、历史事件、像素结果和工具响应被交给了模型，以及模型随后发起了什么动作。对可控任务再结合状态回放、证据消融和任务 oracle，才能把“该动作关联了这些证据”升级为“该证据在给定重放条件下影响了决策/结果”的实验性结论。

## 商业落地场景与客户价值

### 首个产品化场景：企业 GUI 操作 Agent 的可审计执行

首期场景聚焦企业内部的视觉 GUI 操作 Agent：它在经过授权的 CRM、ERP、工单、运营后台或测试环境中读取界面状态，检索历史页面或局部区域，然后填写字段、流转工单、发起受控操作或交由人工确认。其通用循环为：环境返回视觉 observation，Agent 通过受控工具发起动作，动作产生新的状态和画面。

典型失败包括：页面改版后看错字段、基于过期截图重复提交、误读颜色/状态标签、在多窗口/多任务之间混淆上下文、工具返回成功但业务状态未达成。企业真正需要的不是“保存所有截图”，而是能在失败后说明：

```text
这次写入动作由哪个 Agent 在哪个页面状态下发起？
它在动作前取回了哪些历史截图、裁剪或像素读数？
这些证据是否来自同一个业务对象和相同的页面版本？
修复视觉理解或工作流后，能否在沙箱中验证业务结果恢复正常？
```

| 角色 | 关切 | VEP-DR 交付物 |
|---|---|---|
| 企业 AI 平台 / 自动化负责人 | 生产 Agent 的稳定性、成本、风险和可追责性 | 运行台账、失败类别、证据完整率、重放与发布治理指标 |
| Agent 开发与运维人员 | 快速判断错误来自视觉理解、工作流、工具还是环境 | 决策回执、精确的前后状态、证据来源链与可复现重放包 |
| 业务质检 / 审计人员 | 高风险操作是否有充分依据、是否越权或误办 | 与工单/业务对象关联的证据包、批准记录和脱敏回放视图 |
| 最终业务人员 | 操作是否正确、是否需要人工接管 | 更少的错误提交、漏办与重复操作；不直接操作底层证据库 |

商业闭环为：**线上执行 → 异常或人工质检触发 → 决策证据回放 → 修复模型/工具/流程 → 沙箱验证 → 已验证案例沉淀为回归集和发布门禁**。其中，生产系统只接收诊断与处置建议；任何真实写入、回滚或重放均继续受既有权限、审批和业务系统约束。

### 与现有视觉基准的关系

ARC-AGI-3、GameWorld 和 AI GameStore 是验证视觉交互能力的受控环境；其中 VISTA 提供了可借鉴的视觉记忆、主动检查与工具封装实现。它们适合先验证资产完整性、工具语义、回放准确性和证据消融流程。企业 GUI 场景是后续产品化目标，必须单独提供环境适配、身份权限、数据脱敏、业务 oracle 和无副作用的沙箱；不能将游戏里的成功率直接外推为生产自动化效果。

## 现有基础与缺口

本项目调研的 VISTA 是一项重要参考实现：它是视觉交互 harness，而不是新的基础模型或向量检索系统。它保留模型所见的视觉帧，让模型根据任务自行调用 `inspect` 回看指定 `turn/frame/region`，或调用 `read_pixels` 获得像素矩阵；`history` 返回动作和环境结果，`GUIDE.md` / `WORKING.md` 分别保存长期与临时文字记忆。模型不直接拥有宿主文件系统、数据库凭据或环境控制权。

在 ARC-AGI-3 中，宿主侧 `GameController` 在初始状态和每一次环境成功返回 observation 后保存视觉帧；`play` 推进环境，`inspect` 读取历史帧或生成裁剪图，`read_pixels` 从源图采样并返回文本。VISTA 已经形成三类互补记忆：模型当前上下文、模型自己维护的语义笔记、宿主维护的无损视觉证据档案。

本项目已在 `trace_synthesis.vista_runtime` 中实现第一阶段的运行时存储基础：独立的 `vista_trace` schema、`runs`、`steps`、`tool_calls`、`assets`、`observations` 表，以及内容寻址的图片资产、原图到派生图的来源关系、顺序追加和事务完整性约束。阶段计划已明确：目前完成的是 PG 侧契约和读写测试；VISTA live hook、ARC-AGI-3 正式一局、跨进程回放与导出仍属于后续接线和验收工作。

这套基础仍有四个缺口：

- 资产和 observation 被保存，但没有将“实际交付给某一次模型请求的输入集合”建模为一等对象。
- `inspect`、`read_pixels`、`history` 的查询结果分别可查，却不能直接回答“本次 `play` 决策依赖了哪些可观察证据”。
- 当前回放关注能否读回帧和工具结果，尚未定义“同一决策输入包”与“替换某个证据后的对照试验”。
- 视觉截图、裁剪、像素表和文字记忆未形成统一的业务可审计回执，难以支持高风险 GUI 动作的复核与发布治理。

## 为什么要做视觉证据包与决策回执

第一层原因是正确性。当前帧、历史帧、局部裁剪和像素读数具有不同的时间与来源语义。只保存“某一轮有一张截图”无法证明模型在作出写入动作前看到了哪一版页面，也无法区分当前证据、过期证据和由原图派生的证据。

第二层原因是可复现性。视觉 Agent 的问题常在某一时刻、某一区域、某个状态切换后才出现。开发人员需要重建“当时模型收到的图片、文本工具结果和任务状态”，而不是从海量截图目录中人工猜测。

第三层原因是风险控制。对具备副作用的企业 GUI 操作，事后只知道“Agent 点击过按钮”不足以支撑审计。系统需要把动作、证据、权限、确认状态、环境版本和业务结果关联起来；高风险动作应在沙箱验证或人工审批后才进入生产处置。

第四层原因是成本与能力评估。长时视觉 Agent 不应把所有历史图片永久压入上下文。企业需要量化模型究竟检索了多少图像、哪些裁剪被重复使用、图像记忆是否降低重试、哪些任务需要 `read_pixels` 才能避免误操作，以便优化模型 token、存储和人工复核预算。

## 方案设计

### 1. 总体定位

VEP-DR 定位为“**视觉决策证据与可验证回放控制面**”。它兼容采用 `play`、`inspect`、`read_pixels` 和 `history` 等交互工具的运行时，也可适配其他同等语义的视觉 Agent 接口；宿主负责执行环境和读取证据，模型不直接查询数据库。新增层只在宿主侧记录、组织和验证每个决策实际收到的证据。

```text
环境 / 企业 GUI / 游戏
        │ observation、action result
        ▼
交互 Agent Runtime / Controller
        │  play / inspect / read_pixels / history
        ├──────────► 规范化资产与 observation（既有 TraceStore 基础）
        │                         │
        │                         ▼
        │                  Visual Evidence Pack
        │                         │  精确交付的视觉、像素、历史与文本
        ▼                         ▼
模型会话  ◄────────────────  ModelTurn / DecisionReceipt
        │                                  │
        ▼                                  ▼
   受控环境动作                    回放、消融、oracle 与审计回执
```

关键边界是：VEP-DR 记录“哪些输入被交付”和“随后发生了什么”，并不读取或断言模型内部思维过程。模型自述的理由若被保存，应作为 `agent_declared_rationale` 单独标记，不能替代视觉来源、环境状态或重放结果。

### 2. 核心对象

| 对象 | 含义 | 来源与不可变约束 |
|---|---|---|
| `VisualAsset` | 原始或派生图片的字节、SHA-256、MIME、尺寸 | 复用既有 `assets`；相同字节去重，图片本体不可改写 |
| `Observation` | 图片在某个 run/step/moment/view 中的语义位置 | 复用既有 `observations`；保存 `current`、`historical`、`derived` 与来源 asset / transform |
| `EvidenceQuery` | 模型或策略发起的证据请求 | 记录 `inspect`、`read_pixels`、`history` 的参数、调用时刻、返回状态与预算消耗 |
| `EvidenceItem` | 可交付给模型的一项证据 | 引用 observation / asset、像素表、history 事件或受控文本结果；保存来源和内容摘要/hash |
| `EvidencePack` | 某次模型决策前实际交付的有序证据集合 | 记录 pack 版本、item 顺序、视觉 detail、提示词/任务版本和上下文恢复点；不复制图片 bytes |
| `ModelTurn` | 一次模型请求与响应 | 模型、参数、provider、上下文配置、响应/工具调用摘要、输入 pack ID；敏感文本按策略脱敏 |
| `DecisionReceipt` | 一个会改变环境的动作的可审计回执 | action、发起 Agent、前置状态、EvidencePack、权限/确认、环境结果、后续 observation、失败类别 |
| `ReplayCheckpoint` | 可安全恢复的环境与证据锚点 | 环境 fixture/snapshot 标识、版本、必要状态 hash、前序 step、允许的工具策略 |
| `ReplayTrial` | 一次重放或证据对照实验 | 使用的 checkpoint、补丁/移除的证据、重复次数、模型配置、oracle 结果和差异 |

其中 `EvidencePack` 是本方案的关键新增实体：它不是“所有历史的备份”，而是**特定模型决策收到过的、按顺序可重新交付的最小证据清单**。

### 3. 证据包构造与写入协议

一次视觉决策遵循以下过程：

```text
1. 宿主固化当前环境状态与当前 observation
2. 模型按既有证据查询工具主动请求 inspect / read_pixels / history
3. 宿主将每次成功返回的可见结果登记为 EvidenceItem，并保留其来源
4. 在下一次模型请求前，按实际交付顺序冻结 EvidencePack
5. 模型返回 play / 写入 / 确认等动作，宿主创建 pending DecisionReceipt
6. 环境成功返回结果与后续 observation 后，原子完成 receipt；失败则记录真实失败终态
```

对于 `inspect`，包中必须能沿 `derived asset → source asset → observation → step` 回溯，且保存裁剪、放大和 frame 选择参数。对于 `read_pixels`，包引用源 asset、采样区域、行列数、像素协议和文本结果。对于 `history`，包引用事件范围、返回版本和对应的 turn/step。图片、像素表和历史事件都使用引用、hash 与位置描述，避免在多个回执里重复保存大对象。

`DecisionReceipt` 的完成边界与当前 TraceStore 一致：只有环境动作和后续 observation 都成功提交后，动作才是 completed；环境错误、存储错误、无效参数、模型传输/压缩错误或预算耗尽必须保留各自失败类别，不能伪造为“已执行且有完整证据”。

### 4. 证据就绪策略：保留模型主动性，支持高风险动作治理

模型主动决定是否回看历史是本方案保留的核心能力；VEP-DR 不引入一个会静默替模型选图的黑盒检索器。商业 GUI 场景可以在此之上定义可解释的 `EvidencePolicy`，仅对高风险动作增加显式治理：

| 动作类别 | 最低证据要求示例 | 平台行为 |
|---|---|---|
| 只读查询 | 当前页面或工具结果即可 | 仅记录 evidence pack |
| 可逆写入 | 当前页面版本 + 目标对象身份 + 工具返回 | 若关键证据过期，标记风险并建议重新观察 |
| 不可逆/高风险写入 | 当前页面 + 业务规则读取 + 人工确认或沙箱预演 | 默认阻止自动执行或转入审批；不由模型自行绕过 |

“证据过期”必须按环境版本、业务对象 ID、页面版本或状态 hash 定义，不能仅以截图时间判断。该策略在 ARC 等游戏基准中默认关闭，以免改变原始评测语义；在企业 GUI profile 中作为显式配置启用。

### 5. 三层回放与证据消融

VEP-DR 将回放分成强度递进的三层，避免把“重新看到了同一张图”误写为“已经证明视觉证据导致了成功”。

| 层级 | 方法 | 可回答的问题 | 结论边界 |
|---|---|---|---|
| 完整性回放 | 按 `EvidencePack` 读回相同 asset bytes、变换和工具结果 | 数据是否保存完整，派生图是否来自记录的原图 | 只证明证据可重建 |
| 决策输入回放 | 在相同模型/配置下重新交付 pack，记录模型动作分布 | 相同可见输入下模型是否稳定地产生相近动作 | 模型随机性、服务版本变化仍可能造成差异 |
| 证据消融与状态重放 | 在安全 checkpoint 处移除、替换或修正一个 EvidenceItem 后续跑，由任务 oracle 判断 | 某项视觉证据在给定状态与模型配置下是否影响动作或任务结果 | 多证据交互和环境漂移下，只能报告条件性的实验支持 |

例如，Agent 在 CRM 页面上把“已审核”标签误读为“待审核”并重复提交。系统可先完整重建当时的当前图、历史裁剪与像素结果；再在脱敏沙箱中只替换该标签区域的证据或改用 `read_pixels` 结果，比较重复提交动作的出现率和业务 oracle（是否产生重复工单）。如果结果改善，该试验支持“该视觉证据/解析路径在该条件下影响了决策”；它不自动证明线上故障只由一个像素区域造成。

### 6. 数据模型：在既有 TraceStore 上增量扩展

现有 `runs`、`steps`、`tool_calls`、`assets` 和 `observations` 继续是运行事实层。建议新增下列派生表，不改变既有图片资产和环境语义：

| 表 / 关系 | 核心字段 | 作用 |
|---|---|---|
| `model_turns` | `turn_id`、`run_id`、请求序号、provider/model/config 版本、input hash、response 摘要、状态 | 将一次模型输入输出与 runtime step 分开建模 |
| `evidence_queries` | `query_id`、`turn_id`、工具名、参数、状态、预算 | 保存模型如何请求历史图、像素或事件 |
| `evidence_packs` | `pack_id`、`run_id`、目标 `model_turn`、任务/提示版本、上下文恢复版本、完整性 hash | 冻结决策输入集的身份 |
| `evidence_pack_items` | `pack_id`、顺序、item 类型、observation/asset/tool-result 引用、display 方式 | 精确描述视觉和结构化证据的交付顺序 |
| `decision_receipts` | `receipt_id`、`model_turn`、action、环境前后状态、权限/确认、状态、失败类别 | 将“模型动作—环境结果—证据包”连接为审计单元 |
| `replay_checkpoints` | `checkpoint_id`、环境/fixture 版本、状态 hash、前序 receipt、可用性 | 定义安全可恢复的重放起点 |
| `replay_trials` | `trial_id`、checkpoint、基线/补丁 pack、模型版本、重复次数、oracle、统计结果 | 保存回放、消融和验证结论 |

所有派生记录应保存 `source_run`、创建时间、执行器/模型版本和数据分级；事实层只追加。删除或脱敏原始数据时，派生记录应保留“证据已不可用”的状态和哈希，不可伪造仍可重放。

### 7. 运行台账与产品查询

VEP-DR 应提供的是可操作的质量与审计查询，而不是单纯的截图浏览：

```text
某次失败写入动作之前，模型实际收到过哪些当前图、历史图、裁剪和像素结果？
这些证据是否属于同一业务对象、同一页面版本和有效状态？
同一 GUI 元素在多个失败 run 中被怎样检索、裁剪和误读？
模型版本或提示词升级后，高风险动作的 EvidencePolicy 命中率、人工接管率和失败率如何变化？
某条修复建议是否在确定的 checkpoint 和 oracle 下通过了证据消融 / 状态重放？
```

每次高风险动作可生成一个 `DecisionReceipt`：包含业务对象的脱敏标识、动作、证据包摘要、证据来源链、审批状态、环境结果、关联失败类别和可用的重放结论。它可以成为开发调试、业务质检、审计抽查和发布回归的共同输入，而不是由各团队各自维护截图和 Excel 记录。

### 8. 分阶段落地

第一阶段：**完成既有运行时的 live hook 与证据事实闭环。** 在不改变当前工具语义的前提下，实现 `off / dual / pg` 模式的真实接线；先复用 VISTA 的 ARC-AGI-3 适配器，以确定性/可控步骤验证初始帧、`play`、`inspect`、`read_pixels` 的原图、派生图、工具文本、hash 与顺序对账。该阶段只验证“保存与读回正确”。

第二阶段：**引入 EvidencePack 与 DecisionReceipt。** 记录模型请求、实际交付的图片/文本/历史结果和环境动作；实现逐条回执与只读回放页。先以 `sb26` 等受控游戏 run 验证：任意 `play` 都能查到其前置 evidence pack，且同一包能重建为相同的模型输入结构。该阶段不声称模型因果解释。

第三阶段：**建立沙箱重放与证据消融。** 为支持 checkpoint 的任务适配状态恢复；先在 fake environment 或企业 GUI 测试租户中重放，依次验证完整性、决策稳定性和单证据对照。任务 oracle 必须来自环境/业务规则，而非另一个 LLM 的主观评价。

第四阶段：**企业 GUI 试点和治理闭环。** 选择一个低风险、已具备测试环境和明确验收条件的流程，例如工单字段补全或审核状态流转；将已验证失败案例编入回归集，比较发布前后失败重复率、人工复核量和回放成本。通过试点后再扩大到具有更高副作用的业务操作。

### 9. 可观测指标

| 类别 | 指标 |
|---|---|
| 证据完整性 | 可完成动作中有完整 EvidencePack 的比例、pack 可回链至原始 asset 的比例、来源/transform 缺失率 |
| 回放保真 | 原图/派生图字节 hash 一致率、工具结果一致率、状态 checkpoint 恢复成功率、pack 重建成功率 |
| 决策质量 | 环境任务成功率、非法动作率、重试/RESET 率、同输入决策分歧率；按任务、页面版本与模型版本分桶 |
| 证据策略 | 高风险动作的当前状态证据覆盖率、过期证据触发率、人工审批/接管率、策略误拦截率 |
| 验证强度 | 可进入沙箱重放的失败比例、消融试验完成率、oracle 通过率、重复试验方差与置信区间 |
| 资源成本 | 每 run 的 asset 数、去重率、存储字节、视觉输入 token、`inspect`/`read_pixels` 次数、重放时间与费用 |
| 业务价值 | 人工复盘时长、错误重复发生率、发布后回归率、高风险操作的可审计覆盖率；应在试点中实测而非预设承诺 |

## 风险与边界

VEP-DR 不把“模型看到了某张图”解释为“模型理解了这张图”，也不把模型输出的文字理由当成充分因果证据。证据包证明的是宿主实际交付的输入；语义正确性需要环境 oracle、人工复核或受控实验进一步验证。

视觉 Agent 的模型、服务端版本、随机采样、网络延迟和环境状态可能使完全相同的输入产生不同动作。决策输入回放必须报告配置、随机性控制能力和多次运行分布；无法固定的因素属于结论前提，不应被隐藏。

生产 GUI 通常包含客户信息、会话令牌、订单或工单内容。原始图片、像素结果和页面文本必须按租户和数据分级隔离；回执默认保存资产引用、摘要和 hash，面向质检的回放页面做脱敏与字段级授权。模型、浏览器和 Agent 均不获得数据库凭据或任意查询能力。

本方案不替代任何视觉 Agent 的推理能力、不改变 ARC-AGI-3 的官方评分，也不建议在生产环境对有副作用的动作做自动回放。它的创新定位是将主动视觉记忆与现有 TraceStore 基础，提升为能够连接**视觉证据、实际模型输入、环境动作、业务结果和受控验证**的系统能力。VISTA 的视觉记忆实现是重要借鉴和首个验证载体，但不是本方案的定义边界；其真实价值应由受控游戏环境和企业 GUI 试点的端到端数据证明。
